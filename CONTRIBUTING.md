# Contributing

Bug reports and pull requests are welcome. For a larger change, open an issue first so we can agree on the scope.

## Setup

The build uses [Bun](https://bun.sh)'s bundler (`bun build`), pinned to Bun 1.4.4 for builds, checks and publishing, so install that version as well as Node.js 22.12 or later. The format check runs on Bun's `bun fmt` and the type checks on `bun check`, which need Bun 1.4.4 or later; the declaration files are still emitted by `tsc`.

```sh
npm ci
npm test            # builds dist/ first, then the corpus test and the behavior tests (src/ and dist/)
npm run build       # dist/node.js and dist/bun.js, the one-file builds Node and Bun load (bun build)
npm run types       # emits the .d.ts files, then type-checks src/, test/ and conformance/ (not conformance/streams/) and the consumer type test
npm run types:streams  # installs conformance/streams/'s dependencies (npm ci), then type-checks it
npm run types:bench    # installs bench/'s dependencies (npm ci), then type-checks it
npm run check:package
npm run check       # format, lint and all of the above (`bun fmt`, oxlint; npm run format fixes the format)
```

`npm run check` also checks the Python and shell scripts with [ruff](https://docs.astral.sh/ruff/) 0.17.1, [ShellCheck](https://www.shellcheck.net/) 0.11.0 and [shfmt](https://github.com/mvdan/sh) 3.14.1, which are not npm packages: install those versions and put them on your `PATH`. CI installs the same versions.

The tests also run on Bun (`bun test test/`) and Deno (`deno test -A --no-check test/`; `npm run types` does the type checking); run `npm run build` first, because they load `dist/`. Please run the runtimes you have.

## The conformance corpus

`test/corpus.json` holds 3,300+ requests with the signature and canonical request that botocore's S3 signer produces for each. The generator normalizes each path and query itself (`conformance/oracle.py`) before botocore signs the request, so botocore does not check that step; the four examples in the S3 documentation do. The corpus is generated; do not edit it by hand.

```sh
python3 -m venv .venv && .venv/bin/pip install -r conformance/requirements.txt
PYTHON=.venv/bin/python npm run conformance      # rewrites every test/corpus*.json
```

The other signers have their own corpora (`test/corpus-general.json`, `corpus-presign.json`, `corpus-v4a.json`, `corpus-stream.json`), generated by `node conformance/build-more.mjs` (the same Python environment, plus `npm ci` in `conformance/streams` for the AWS SDK's signer). The general and presign ones are seeded and rebuild byte for byte; the SigV4a one does not, because ECDSA is randomised.

A change to the signing code must keep every case passing. A bug fix needs a case that fails before the fix: add it to the generator (`conformance/cases.mjs`, `general-cases.py` or `presign.py`) and regenerate.

## Scope

sigflint signs requests for every AWS service with SigV4, as headers or presigned URLs, plus SigV4a, chunked uploads and event streams. Anything else is not in 1.0; an issue describing the use case is the place to start.

The package has no dependencies and uses only what the runtime provides. A change that adds a dependency, or that makes any workload slower, needs a measurement (`bench/`) that shows why it is worth it. Each signer stays in its own module and export, with no work at import time, so a bundle holds only what it imports.

## Releases

Before every version bump, re-run the speed, memory, import and size measurements on the code being released (`bench/`; the protocols say how), regenerate the charts and tables, and correct every README and CHANGELOG number. Then run `node bench/check-benchmarked.mjs --record`. The publish workflow runs `npm run check:benchmarked` and stops when the recorded version or the `src/` tree differs from the tag. [AGENTS.md](AGENTS.md) has the rest of the release steps.
