# Protocol: the re-run with a host check around every pair

Declared before the counted runs (2026-10-17), in the worktree that holds the results.

Question: do the speed, memory and import figures of `protocol-rerun-2.md` still hold when no figure is kept unless the host was quiet right before and right after it was measured? That run gated every process on whole-machine Linux CPU only and checked the host (Linux and native Windows CPU, memory and I/O pressure, swap) once before and once after each part. Alternating Node and Bun samples that were checked per pair (`results/rerun-2-alternating.md`) gave Bun times 25% to 40% lower than the unchecked rounds on some rows while Node moved 2% to 10%, so the wall-clock figures of that run, Bun's in particular, were probably too slow. Counts and bytes (heap per call, collections, peak memory, retained heap, bundle sizes) do not depend on how busy the host is, but they are measured again here because the parts are run again whole.

Candidate: the same build as before, `dist/node.js` (`439a387d`) and `dist/bun.js` (`21a8a862`), built from `src/` at git tree `712d1eb2`, read from a hashed copy (`SHA256SUMS` is checked first; hashes in `results/more-artifacts.sha256`). If `src/` changes before the record, every part is void.

Plan: the parts, arms, workloads, runtimes, harness scripts, 3 rounds by default, rounds 4 and 5 for a whole part only when a claim comparison is unsettled after round 3 (decided from the part's own analysis and written next to the results first), the cap of 5, 7 import processes per arm, runtime and round, the 20% per-process busy gate with up to 8 retries, the A/A noise floor and the band `max(3%, 2 x A/A spread)` (6% floor for allocation), normal priority, all CPUs, no `nice` or `taskset`, and the unsettled-comparison rule are those of `protocol-rerun.md` and `protocol-rerun-2.md`, unchanged. The harness scripts are not changed; only the driver is new (`run-admitted.sh`).

What is different, declared here:
- **Unit and pair.** A unit is one library (arm) in one round, measured under Node and under Bun back to back, one process at a time. Node goes first in odd rounds and Bun first in even rounds; the library order is reversed in even rounds. For the import part a unit is a whole round (7 fresh processes per library and runtime, both runtimes), because one process takes about 0.2 s.
- **Admission.** A host check runs before the first unit of a part and after every unit; the check after a unit is also the check before the next unit. It requires at most 4 combined busy cores (Linux and native Windows over one aligned 10 s window, the host VM's own CPU on the Windows side excluded), at least 8 GiB available on each OS, memory full pressure at most 10 ms and I/O full pressure at most 100 ms in any second, and no swap-out or writeback. A unit counts only when the check before it and the check after it both admitted. A unit that fails is kept in `results/rerun-3-not-admitted.jsonl`, not in the results, and measured again; after 4 failed attempts the run stops and gives up the host lock, to be started again. A unit with any process rejected by the per-process gate or any errored process also fails. Every check's receipt, and every unit's attempts, are in `results/rerun-3-admission.jsonl`.
- **Lock.** Each part holds the shared host lock from its first check to its last and gives it up when it ends or when the host is not quiet for 3 checks 30 s apart.
- **Old data.** The 2026-10-16 raw results move to `results/rerun-2-per-process-gate/` and are not pooled with the new ones. The figures in the README and `docs/benchmarks.md` are the new ones.
- **Import processes.** An import process takes about 0.2 s, so the per-process Linux busy gate is applied once before each repetition of nine import processes (the control and the eight arms), not before each one; the host checks around the round still apply. The driver (`run-admitted.sh`) is the one used for the counted runs apart from two changes made afterwards that can only refuse more: a host check now counts only when the check command exits 0 as well as printing an admitting verdict, and a cache process whose busy gate never quiets now fails its unit. The first cannot have changed a result, because the check command exits 0 exactly when it admits; the second would have shown as a missing row, and the data has every cache row (5 per arm and runtime) and every import row (63 per runtime and round).
- **Limits that remain.** There is still no continuous observer of native Windows CPU during a timed process, so load that starts and ends between two checks is not seen, only the Linux per-process gate would show it (and only if it is Linux CPU). Pairs make a runtime comparison fair to the extent that load is steady across the two processes of a unit, which the checks around the unit support but cannot prove.

Claim status: a confirmation, or a correction, of the figures in the README and `docs/benchmarks.md` for the released code. A change inside the band is "no clear change". Dispositions for Node-ahead rows are re-derived from the new pairing (`node pair-node-bun.mjs`); a row that flips or newly appears is a new case for the maintainer to decide on, and nothing is filed for it from this run.
